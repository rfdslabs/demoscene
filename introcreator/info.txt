If by “crackintro/cracktro” you mean old-school demoscene-style intros with animated logos, scrollers, plasma/tunnel effects, chiptune music, synchronized transitions, etc., macOS is a good platform for this.

For a modern Mac, I would use this stack:

C++20
│
├── SDL3
│   ├── window
│   ├── keyboard/input
│   └── audio output
│
├── Metal
│   └── almost every visual effect
│
├── ARM64 Assembly
│   └── selected CPU/synth/math routines
│
└── Tiny procedural synth
    └── music generated at runtime

SDL3 has native Metal integration on macOS through a CAMetalLayer, so you can keep the program mostly C++ while talking directly to Metal. Apple also provides Metal-cpp specifically to expose Metal through C++ with essentially no wrapper overhead.

For something that looks like an actual cracktro, I would structure the runtime around a single global timeline:

struct DemoState {
    double time;
    double beat;
    int scene;
};

void frame(DemoState& s)
{
    if (s.time < 8.0)
        logoIntro(s);
    else if (s.time < 20.0)
        plasmaScene(s);
    else if (s.time < 36.0)
        tunnelScene(s);
    else
        finale(s);
}

But don't use wall-clock time as the ultimate synchronization source. Make the audio sample position the master clock:

samplePosition
      │
      ▼
   seconds
      │
      ├── BPM / beat
      ├── scene changes
      ├── flashes
      ├── logo movement
      ├── palette changes
      └── shader parameters

That gives you the classic music-synchronized presentation.

For graphics, put almost everything in Metal shaders. Apple explicitly positions Metal as direct GPU access for graphics and compute, and modern Apple Silicon is extremely well suited for shader-heavy procedural effects.

A fullscreen triangle plus a fragment shader is enough for most old-school demo effects:

fragment float4 cracktro(
    VertexOut in [[stage_in]],
    constant Uniforms& u [[buffer(0)]])
{
    float2 uv = in.uv * 2.0 - 1.0;
    float t = u.time;

    float v =
        sin(uv.x * 10.0 + t) +
        sin(uv.y * 13.0 - t * 1.4) +
        sin(length(uv) * 20.0 - t * 2.0);

    float3 col =
        0.5 +
        0.5 * cos(
            float3(0.0, 2.0, 4.0) +
            v +
            t
        );

    return float4(col, 1.0);
}

On a current Apple Silicon Mac, your assembly should be ARM64/AArch64, not x86-64. Clang/Xcode handles C++ and assembly well, and Apple's current toolchain supports modern C++ through Apple Clang/libc++.

For example:

// add4.S
.text
.align 2
.global _add4

_add4:
    fadd s0, s0, s1
    fadd s0, s0, s2
    fadd s0, s0, s3
    ret

C++:

extern "C" float add4(float, float, float, float);

float x = add4(1.f, 2.f, 3.f, 4.f);

More interesting is NEON:

.global _mix4
.align 2

_mix4:
    // q0 = four float samples
    // q1 = gain
    fmul v0.4s, v0.4s, v1.4s
    ret

That gives you the same spirit as classic demo coding, although for graphics you shouldn't force CPU assembly where Metal shaders are massively faster.

For music, I would not start with MP3/AAC. Generate the soundtrack.

A tiny synth can have something like:

float osc(float phase)
{
    return sinf(phase * 6.28318530718f);
}

float synth(double t)
{
    float bass =
        osc(t * 55.0) * 0.25f;

    float lead =
        osc(t * 220.0 +
            sin(t * 3.0) * 0.3) *
        0.15f;

    return bass + lead;
}

SDL3's current audio API is centered around SDL_AudioStream, including callback-driven generation and conversion/resampling.

A song can therefore literally be data:

constexpr uint8_t bass[] = {

If your goal includes the traditional demoscene obsession with tiny executables, I'd go further and remove SDL once the engine is working:

             Development               Purist version

Window       SDL3                 →     Cocoa/CAMetalLayer
Graphics     Metal                →     Metal
Audio        SDL3                 →     CoreAudio
Music        custom synth         →     custom synth
Code         C++                  →     C++ / ARM64 ASM
Shaders      Metal                →     Metal
Assets       PNG/WAV/etc          →     generated procedurally

That leaves a very small native macOS executable. Apple documents using a CAMetalLayer directly for macOS Metal presentation, including optimized direct-to-display behavior on Apple Silicon when fullscreen.

The important conceptual point is: don't write the graphics renderer itself in ARM assembly. On a 2026 Mac, the spiritual successor to handcrafted graphics assembly is Metal Shading Language. Use ARM64 assembly for the parts where you want the low-level challenge, such as your synth, NEON DSP, PRNG, decompression, procedural data generation, or specialized math. Use Metal for the visual insanity.
